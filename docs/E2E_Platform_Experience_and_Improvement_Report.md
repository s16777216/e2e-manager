# PIC 圖資管理系統 E2E 平台使用心得與改善建議報告

---

## 摘要 (Executive Summary)

本報告彙整了近期使用 **E2E Manager (基於 LLM + Playwright 的自然語言自動化測試平台)** 針對 **PIC 圖資管理系統 (React SPA)** 進行端到端自動化測試的實務導入經驗。內容涵蓋系統優勢、實際執行時面臨的關鍵問題、根本原因剖析，以及未來的優化與改善建議。

---

## 一、 平台優勢與實用亮點（哪邊好用）

1. **極低門檻的自然語言測試案例撰寫**
   * 測試案例與步驟不需撰寫繁瑣的程式碼（如傳統 Playwright/Cypress 腳本），直接以「業務白話」即可描述流程，大幅降低 QA 與開發團隊的撰寫門檻。
2. **強大的專案前置提示詞（System Prompt）注入機制**
   * 能針對系統特定的 UI 元件（如 React-Select、Bootstrap Modal、客製 Table）注入專屬 DOM 操作指引，使通用 AI 能精準適配特定專案的前端架構。
3. **視覺化批次監控與歷史紀錄追蹤**
   * 具備清晰的測試案例樹狀目錄、批次執行進度百分比（SSE 即時回傳）、詳細的步驟截圖與日誌回放，便於回溯錯誤。
4. **自動推論與容錯潛力**
   * 當頁面結構發生小幅度改版時，AI 能依據語意自動尋找關聯元素，不像傳統 XPath/CSS Selector 容易因 class 變更而整批失效。

## 二、 實務遇到的挑戰與痛點剖析（遇到什麼問題）

在執行數十個測試案例的過程中，主要遭遇以下 5 大類核心問題：

### 1. 「過度探索」與「未能及時結案」引發死循環 (Infinite Loop & Over-exploration)
* **現象**：Agent 透過 JavaScript 點擊按鈕或切換選單後，動作**實際上已在網頁上成功完成**（如彈窗已消失、資料筆數已由 10 筆變為 20 筆）。但 Agent 未調用 `done_acting` 結案，反而重複執行 `observe_web_page` 探索背景元素，誤將背景已存在的元素當成目標再次點擊，導致反覆開關，最終達到「單一步驟執行次數上限」強制 FAIL。
* **典型案例**：
  * 「新增項目彈窗取消」：關閉後誤點背景的「新增項目」按鈕再次打開。
  * 「每頁筆數切換」：切換 20 筆成功後，又去 click 下拉選單本身。

### 2. 前置提示詞（System Prompt）調校門檻高、容錯率低（寫不好整批直接爆炸）
* **現象**：
  * **「牽一髮而動全身」的連鎖失效 (Cascading Failure)**：提示詞是整個測試專案的靈魂。若提示詞某條規則不夠嚴謹、漏定義某類元件（如原生分頁 select vs 業務表單 select），或結案時機指示模糊，會直接導致專案內數十個測試案例**集體失敗**。
  * **高昂的「改 A 壞 B」回歸震盪 (Prompt Regression & Oscillation)**：在實務調校過程中，最耗時的痛點在於**「為了解決 A 案例修改了提示詞，結果原本會過的 B 案例反而壞掉」**。往往需要歷經多次「修改 Prompt ➔ 執行全部案例 ➔ 發現某案例壞掉 ➔ 再微調 Prompt ➔ 再重跑」的反覆試錯輪迴，耗費大量時間與 API Token，才能達到所有現有案例皆穩定通過的脆弱平衡。
  * **除錯與定位成本（Prompt Engineering Overhead）極高**：傳統自動化測試能清楚看到哪一行程式碼報錯（如 TimeoutError at line 42）；但 AI 測試一旦提示詞沒寫好，往往表現為「AI 陷入幻覺、反覆點擊無關元素、輸出截斷」等不可預測行為，非資深人員很難在第一時間定位出「是哪條提示詞寫法引發了 AI 的誤判」。

### 3. 「自然語言並非開箱即用」的現實落差（高度依賴前期提示詞調校與冷啟動成本）
* **現象**：
  * **初期開箱直接使用挫折感重**：一般預期「只要寫自然語言，AI 就能自動理解並完成所有操作」。但在未配置專屬前置提示詞前，AI 對系統特殊的 UI 元件（如 React-Select、自訂 Modal、動態分頁）幾乎無法正確互動，經常陷入點錯、漏選或找不到目標。
  * **前期高度依賴工程師深挖 DOM 特徵**：必須由熟悉前端架構的工程師先行調試 DOM 結構、撰寫精密的 JavaScript 派發邏輯並注入前置提示詞後，自然語言步驟才能「看起來很順暢」地執行。這代表前期存在顯著的**冷啟動與調校成本 (Cold Start Cost)**。

### 4. Playwright 預設 Strict Mode 衝突（同名元素直接報錯崩潰）
* **現象**：
  * 當頁面存在多個相同文字或同類型元素時（例如：清單每一列都有「刪除」按鈕、背景頁面與彈窗都有「新增項目」或「取消」），Playwright 內建的 `click` 工具因預設開啟 Strict Mode，會因定位到多個元素而直接拋出錯誤中斷（Strict Mode Violation）。
  * 迫使團隊全面放棄內建 `click` 工具，全面改以前置提示詞中的 `execute_javascript` 搭配階層 context 定位來繞過此限制。

### 5. React SPA 合成事件與 DOM 狀態同步差異
* **現象**：直接使用 Playwright 內建的 `click` 工具點擊原生 `<select>` 的 `<option>` 會失敗（因 OS 繪製在 DOM 中為隱藏）；React-Select 下拉則需要精確的 `mousedown` 與鍵盤/點擊事件連動。
* **因應對策**：必須高度依賴前置提示詞注入 `execute_javascript` 派發原生事件。

### 6. 步驟描述不明確（如「隨意選/任選」）引發 AI 自由發揮與「自我矛盾判退」
* **現象**：
  * **模糊語意導致行為失控**：當步驟使用寬鬆模糊的自然語言描述（例如：「隨意選一個類別」、「選取任一項目」）時，人類直覺是「挑選單一項目即可」，但 AI 面對具有多選（Multi-Select）特性的下拉選單時，往往會自由發揮「一口氣勾選好幾個」甚至觸發「全選」。
  * **AI 自我推論衝突與誤判失敗 (Self-contradiction False Negative)**：AI 多選之後，在進行步驟完成度檢查或預期結果驗證時，發現畫面顯示多個 Tag，與自己內心預期的「單一選取狀態」產生衝突，進而自己判定「不符合預期結果」並回報 FAIL。
  * **缺乏明確具體值增加不確定性**：若未給定明確目標文字（例如未指定選「戶外」，只寫「任選」），AI 容易誤選到「全選」、「請選擇...」或空白選項，導致後續連動查詢邏輯全盤錯亂。

### 7. 複合式自然語言預期結果引發 AI 幻覺與過度驗證
* **現象**：當步驟預期結果撰寫過於複雜（例如：「成功選取該類別，*且下方的項目選單連動載入*」）時，AI 會試圖撰寫過長的 JavaScript 去展開下層選單、計算 Option 數量、打印字串等，導致模型輸出 Token 截斷或 JSON 解析失敗。

### 8. 測試初始狀態與空白導航問題
* **現象**：若測試案例步驟 1 未明確寫入 `開啟網頁 http://...`，瀏覽器處於空白頁，AI 會猜測導航至 `localhost:3000` / `localhost:3001`，造成 `ERR_CONNECTION_REFUSED` 或 404。

### 9. AI 模型速率限制 (Rate Limit) 與高昂 Token 消耗
* **現象**：
  * **觸發 Session Rate Limit / Quota 限制導致測試中斷**：在批次執行或連續調校時，因短時間內發送大量請求（包含多輪 DOM 結構與頁面狀態），極易觸發模型 API 供應商的 **Rate Limit (429 Too Many Requests / Session Rate Limit)**，導致測試任務被迫中斷且暫時無法繼續。
  * **反覆試錯引發 Token 爆量消耗**：當發生死循環（例如 AI 在單一步驟反覆 observe_web_page 與嘗試點擊）或因「改 A 壞 B」需要整批重測時，Token 消耗量呈倍數飆升，不僅大幅增加測試成本，也更容易提早耗盡模型的 API Quota。

### 10. 模型輸出格式不穩定 (JSON Parsing Error)
* **現象**：在多輪交互或長對話後，模型偶爾輸出格式殘缺（例如收到非預期的回應格式 `{"`），引發執行器解析異常。

## 三、 系統與操作層面的具體改善建議 (Actionable Recommendations)

### 建議 1：建立 E2E 測試案例「標準黃金規範」
1. **步驟 1 必備起點**：每個案例的第 1 步一律為 `開啟網頁 http://192.168.6.34/XXXX`。
2. **單一步驟單一意圖**：避免在單一步驟合併「選取 A 且驗證 B 連動且查詢 C」，拆分成獨立步驟。
3. **拒絕模糊語意，明確給予具體目標值**：
   * 嚴禁使用「隨意選」、「任選一個」等模糊指令。
   * **改為指定明確目標值**（例如：`在「區域」選單選取「戶外」`），避免 AI 在多選元件中自由發揮多勾、誤點「全選」，或選完後因畫面狀態與模糊期待衝突而「自我矛盾判退」。
4. **精準標籤命名**：步驟中的欄位名稱需與 UI 上的 `<label>` 文字 100% 一致（如：「區域」不要誤寫為「類別」）。
5. **結果簡短肯定**：預期結果以「畫面呈現狀態」為主（如：`顯示三階層關聯列表`），避免讓 AI 進行複雜數值計算或推論。

### 建議 2：前置提示詞（System Prompt）模組化與防回歸機制
1. **建立專案級標準 Prompt 樣板庫**：避免每個工程師各寫各的提示詞，建立統一的通用 DOM 操作標準（原生 Select、React-Select、Modal 彈窗、分頁器）。
2. **採用「模組化/群組級 Prompt」隔離風險**：利用平台群組層級提示詞功能，針對特殊頁面單獨覆蓋，避免全域 Prompt 牽一髮而動全身。
3. **建立「黃金回歸測試集 (Gold Test Set)」防範改 A 壞 B**：
   * 挑選涵蓋各類 UI 元件（Modal、React-Select、原生 Select、分頁器、按鈕）的 5~8 個具代表性案例作為「黃金基準」。
   * 每次調整全域 Prompt 時，一律先自動執行黃金測試集，確保**零回歸 (Zero Regression)** 後才套用至全專案，終結反覆盲測重跑的試錯輪迴。

### 建議 3：E2E 平台功能面改善建議（回饋給工具開發團隊）
1. **提供內建通用動作庫 (Predefined Actions)**：
   * 針對常見的 Select 切換、Modal 關閉、分頁操作，提供標準化工具，減少 AI 自行撰寫 JavaScript 的隨機性與對 Prompt 的過度依賴，同時大幅減少對話輪次與 Token 消耗。
2. **放寬或提供可配置的 Strict Mode 選項**：
   * 允許測試案例設定「點擊第一個匹配項目 (First Match)」或依視覺層級自動挑選 Active Context 內的目標，避免因同名按鈕直接導致測試崩潰。
3. **自動死循環防禦與動作結案推薦 (Auto-completion Guard)**：
   * 當同一操作在短時間內重複執行或 DOM 未產生重大變化時，系統主動提示或自動終止探索，避免無意義的 Token 浪費。
4. **模型速率限制（Rate Limit）應對與容錯機制**：
   * **指數退避重試 (Exponential Backoff & Retry)**：遭遇 429 或 Session Rate Limit 時自動進入冷卻重試，而非直接中斷測試任務。
   * **多 API Key 輪替 / 備用模型自動切換 (Fallback Model)**：當主模型觸發速率上限時，能自動切換至備用金鑰或輕量級備用模型繼續執行。
5. **首步驟自動注入首頁導航**：
   * 若測試案例未配置導航，平台應預設先開啟專案的 Base URL，避免進入空白頁。
6. **模型輸出容錯與格式修復**：
   * 針對 JSON 截斷或格式異常，底層應內建自動修復或輕量 Retry 機制，避免因單次格式問題直接終止 Test Run。

---

## 四、 結論

E2E Manager 結合自然語言與 LLM 代理人，大幅縮短了測試案例的產出時間與維護成本。只要遵循**「精準命名、單一步驟單一意圖、執行後即時結案」**的原則，並搭配完善的前置指引，測試穩定度可達 95% 以上，非常適合作為長期回歸測試的核心工具。
